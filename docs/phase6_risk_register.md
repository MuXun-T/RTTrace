# Phase 6 Risk Register

Date: 2026-07-09

This register uses the P6.0/P6.1 approval boundary. "Blocking" means the current implementation should stop until the main agent reviews the issue.

| ID | Risk Description | Impact | Mitigation | Blocking | Trigger Handling |
|---|---|---|---|---|---|
| R1 | Scope creeps into P6.2+ during P6.0/P6.1. | Later-phase code could appear without reviewed schemas or claim boundaries. | Keep this window to docs, schemas, mirrored assets, stub metadata, and tests. | Yes | Stop implementation and request main-agent approval. |
| R2 | Synthetic benchmark is questioned as not realistic enough. | Later paper claims may be weak if synthetic cases are overstated. | Keep synthetic material report-only and require later review before any real-RTOS generality claim. | No | Reword claims and defer realism claims until real or reviewed RTOS data exists. |
| R3 | Diagnosis top-k root cause is written as a strong claim. | Accuracy claims would lack approved benchmark evidence. | Mark initial top-k root cause as report-only. | Yes | Change boundary to report-only and rerun schema tests. |
| R4 | Advisor or LLM explanation is mistaken for root-cause truth. | Explanation text could replace deterministic evidence or known labels. | Treat explanations only as review artifacts. | Yes | Stop any truth-path integration and request review. |
| R5 | LLM output pollutes proof digest or proof hash input. | Breaks Phase 5 proof isolation and archived evidence claims. | Keep advisor/LLM fields out of proof paths and assert forbidden fields in schema tests. | Yes | Stop, report diff path, remove the pollution, and request main-agent intervention. |
| R6 | Proof hash semantics are changed. | Existing packages and proof parity become incomparable. | Do not edit proof models, proof export logic, or proof schemas. | Yes | Stop and request main-agent intervention with the diff path. |
| R7 | Evidence package replay and full trace results disagree in a later phase. | Replay equivalence claims would be invalid. | P6.0/P6.1 only define metadata; P6.3 must define equivalence before implementation. | Yes for P6.3 | Do not claim replay; freeze a written equivalence definition before coding replay. |
| R8 | `stale_sidecar` or `corrupt_segment` cases break existing normal tests. | Negative fixtures could leak into normal pipelines. | In P6.1 keep them metadata-only; later fixture work must isolate negative cases. | Yes if tests regress | Remove or isolate the fixture and rerun affected normal tests. |
| R9 | Human feedback schema turns into over-development. | P6.6 could add UI, database, or study infrastructure prematurely. | Keep human feedback out of this window and require separate approval. | Yes | Stop and move the work to P6.6 planning. |
| R10 | Real hardware dependency is introduced. | Tests become non-reproducible in CI and local regression. | Use logical references only in P6.1; later hardware traces must be optional and reviewed. | Yes | Remove hardware dependency and replace it with metadata or fixture references. |
| R11 | Benchmark data becomes too large for CI or focused regression. | Regression runtime and repository size grow unexpectedly. | Keep P6.1 fixture metadata-only and small. | Yes if generated data appears | Delete generated artifacts and defer size policy to P6.2/P6.7 planning. |
| R12 | Phase 6 changes break the Phase 5 sandbox or advisor gate. | Existing safety claims regress. | Run existing advisor and agent tests after P6.0 and P6.1. | Yes | Stop, inspect failing sandbox/gate tests, and request main-agent intervention. |
| R13 | Phase 6 is expanded into a general anomaly detection system. | Scope and claims become unsupported. | Limit language to known-root-cause RTOS diagnosis metadata and future approved benchmark work. | Yes | Remove anomaly-detection claims or code and re-review scope. |
| R14 | P6.2+ is mistaken as already approved. | Future phases could proceed without review. | Scope note, checklist, schema boundaries, and fixture notes state P6.2+ is not approved. | Yes | Change status to not approved and request main-agent review if ambiguity remains. |
| R15 | Pre-approval documentation is mistaken for an implementation artifact. | Planning text may be cited as completed benchmark evidence. | Label pre-approval and P6.0 documents as planning/scope artifacts only. | No | Reword document references and keep implementation claims tied to tests/artifacts. |
| R16 | Stub fixture is mistaken for real trace evidence. | Schema-only metadata could be cited as benchmark completion. | Stub suite states metadata-only, no traces, no evidence packages, no replay result. | Yes | Change claim class to report-only/not-claimable and rerun schema tests. |
| R17 | Benchmark metadata is mistaken for proof facts. | Metadata could be pulled into proof or root-cause truth paths. | Keep diagnosis schemas independent from proof digest and existing benchmark schemas. | Yes | Stop and remove any proof-path coupling. |
| R18 | Existing runtime benchmark schemas are modified. | Runtime optimization contract could be polluted by Phase 6 semantics. | Add independent RTOS diagnosis schemas only. | Yes | Stop, report diff, and request main-agent intervention. |
| R19 | `parser/evidence_models.py` is modified. | Proof and evidence model compatibility could shift. | P6.0/P6.1 do not need runtime model edits. | Yes | Stop and request main-agent intervention. |
| R20 | Collector hot path is modified. | Real trace collection behavior and C++ tests could regress. | P6.0/P6.1 do not touch `collector/`. | Yes | Stop and request main-agent intervention. |
| R21 | Stub suite fails to cover all eight approved case kinds. | P6.1 acceptance and later fixture planning become incomplete. | Add exactly eight metadata-only cases, one per case kind. | No | Fix fixture and rerun schema tests. |
| R22 | `claim_class` boundary is unclear. | Report-only and not-claimable items may be cited as hard claims. | Use only `claimable`, `report_only`, and `not_claimable` with explicit boundary entries. | Yes | Reclassify ambiguous entries and rerun schema tests. |
| R23 | Fake paths or fake artifacts are treated as real trace dependencies. | Tests could silently depend on unavailable artifacts. | Use `logical://` references only and no absolute paths. | Yes | Replace path-like values with logical references. |
| R24 | Tests only check JSON presence and not forbidden fields. | Proof and secret fields could enter unnoticed. | Add negative schema tests and recursive fixture text checks for forbidden names. | Yes | Add the missing negative test before accepting P6.1. |
| R25 | Untracked docs, ignored files, or build artifacts are accidentally included in a later commit. | Commit contains unrelated or sensitive local files. | Final audit uses `git status --short --untracked-files=all`, diff checks, and secret scans. | Yes | Remove unrelated files from the commit set and re-run audit. |
| R26 | Closeout manifest records nondeterministic time, absolute paths, secrets, or participant-level data. | The artifact cannot be safely reproduced or shared. | Use explicit manifest IDs, repository-relative paths, no clock fields, and focused forbidden-content tests. | Yes | Reject/regenerate the manifest and rerun validation. |
| R27 | `reference_only` is presented as replay success. | Replay and proof claims become false. | Assert `replay_pass_count=0`, `reference_only_count=8`, and `all_replay_passed=false` in the manifest and tests. | Yes | Correct the claim or validator before closeout. |
| R28 | P6.7 silently changes a frozen P6.2-P6.6 semantic, proof/export/collector boundary, or benchmark schema. | Historical frozen evidence becomes incomparable. | Audit diff paths and frozen files; permit only approved closeout artifacts and additive management-document status. | Yes | Stop closeout, revert the out-of-bound change, and request review. |
| R29 | Synthetic feedback is interpreted as a human study or descriptive values as usability evidence. | Human-effect or correctness claims lack real evidence. | Preserve zero real participant counts and false claim flags; list real-study requirements as unresolved gaps. | Yes | Correct the document/manifest and rerun focused checks. |
| R30 | Paper-readiness text overstates engineering completeness as empirical validation. | Publication claims exceed available evidence. | Use separate engineering, synthetic, empirical-systems, human-evaluation, and paper-claim readiness layers. | Yes | Downgrade the statement to the evidence level supported by artifacts. |
| R31 | Final regression counts are stale or asserted without the actual full run. | The manifest misrepresents verification status. | Write counts only from the final recorded run and compare them in closeout tests. | Yes | Re-run the complete suite, update the manifest fixture, and revalidate. |
