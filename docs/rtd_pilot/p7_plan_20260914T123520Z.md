# RTD-PILOT P7 Plan: Frozen-Input Gate and Blocked Baseline Framework

Status: planning only; not implementation authorization.

## 1. Objective, scope, and completion criteria

The RTD-PILOT Phase 7 objective in the governing implementation plan is a fair
baseline, ablation, and evaluation framework after a Phase 5 independent-truth
Case hierarchy and deterministic Phase 6 diagnosis output.  This repository's
P6 freeze instead records a `synthetic/report-only closeout; no new P6 capture
or truth generation`.  It cannot satisfy the Phase 7 preconditions.

Accordingly, the only P7 work authorized by this plan is a small, append-only,
fail-closed gate that verifies the frozen P6/P5 inputs and emits one P7
`BLOCKED` record when (and only when) the required independent Case/Observer
truth, Phase 5 Case hierarchy, and admissible deterministic diagnostic inputs
are absent.  It does not implement a baseline, scorer, ablation, mask, split,
evaluation, or a new claim.  This is intentionally narrower than the future
Phase 7 envelope and prevents synthetic substitution.

Completion criteria for this P7 gate are:

1. The supplied P6 commit/tree and all listed P6 frozen material hash-match.
2. The P5 frozen-input audit is rerun read-only and passes.
3. The tool detects that the P7 preconditions are absent without inspecting or
   deriving Observer truth from any prohibited source.
4. One uniquely identified, schema-validated P7 `BLOCKED` record and its
   append-only SHA-256 manifest are written to a new output directory using
   exclusive creation; every file is manifested.
5. The record contains source refs, paths, SHA-256, identity, lineage,
   episode handling, parent record links, blocker reasons, and explicit
   `hardware_action: false` / `truth_boundary` fields.
6. Focused, P5/P6, schema and full regression checks pass; protected inputs
   remain byte-identical.  This completes only the blocked P7 gate, not the
   governing plan's baseline/evaluation Phase 7 or a readiness claim.

## 4. Evidence and record contract

`rtd_p7_frozen_gate.py` must reuse the P6 audit's standard-library patterns:
SHA-256 over bytes, JSON parsing, `os.open(..., O_CREAT | O_EXCL)`, fsync, and
the current `tool/rtd_p6_frozen_input_audit.py` read-only P5 validator.  It
must reject a pre-existing output directory before any output creation.

Every generated P7 JSON record has a declared P7 schema/version, `record_id`,
`record_type`, `phase: "P7"`, `created_at`, `append_only: true`,
`hardware_action: false`, `identity`, `lineage`, `source_refs`, and
`truth_boundary`.  `source_refs` are repository-relative paths (no absolute
paths), each with a role and re-computed SHA-256.  Records must cite the frozen
commit/tree and the canonical P6 record IDs; `lineage.parent_record_id` points
to `record:p6-execution-20260914T181500Z`, while dependent P7 records list all
prior P7 record IDs.  An episode is not fabricated: the blocked record uses
`episode: null` plus `episode_status: "not_applicable_no_capture"`; no
capture/case/episode identity is synthesized.

The P7 blocked record's allowed conclusion is limited to: P6 is an intact,
synthetic/report-only baseline and does not provide the real independent
Observer truth, Phase 5 Case hierarchy, or eligible method outputs required
for P7 evaluation.  Its source refs are the six P6 files above plus the P5
audit invocation result.  The execution, manifest, and regression records cite
the preceding P7 records by ID and hash.  The manifest enumerates every P7
file in its own unique output directory except itself, and the execution record
links the manifest hash.

Identity is only commit/tree plus the P6/P5 record IDs and fixed P7 gate ID;
no `case_id`, `capture_id`, fault class, manifestation status, or label may be
invented, decoded, or exposed.  Verify unique P7 record IDs, unique manifest
paths, one canonical P6 binding, no duplicate source ref identity, matching
commit/tree/hash, and no source path crossing from an uncanonical/superseded
P6 run.  Any stale source hash, record-ID duplicate, P5/P6 tree mismatch,
unresolved parent, divergent record family, or source-ref path outside the
allowlist is a hard failure with no P7 conclusion.

## 5. Retention and no-overwrite policy

All attempts, including failed writes after a record exists, retries, invalid
inputs, corrections, superseded records, duplicate runs, and non-manifested
files, are retained.  The writer must never delete, rename, overwrite, amend,
or reuse an output directory.  A failed pre-write validation produces no
formal P7 record; the command's stderr and exit result are only test/log data.
Once a P7 record exists, any later factual correction is a new unique
`P7_CORRECTION` record with `correction_of`; a replacement conclusion is a new
`P7_SUPERSEDES` record with `supersedes`; it cannot alter the original or its
manifest.  A duplicate logical run is retained under a new directory and
explicitly marked `SUPERSEDED_NON_MANIFESTED`, following the frozen P6 pattern.
An invalid/missing/stale source is `INVALID`/`BLOCKED`, never silently repaired.

No split occurs because no Case/Capture dataset is admitted.  The gate must
assert this before writing: `evaluation_split: "not_applicable_no_eligible_cases"`.
If future P7 opens only after its prerequisites, split membership is
case/template-scoped and predeclared; a capture, mask, retry, or correction
cannot cross a case/split boundary.  This plan retains, rather than discards,
any such violation as a new invalid/correction record.

## 6. Truth and claim boundary

Observer truth remains only independently produced Observer/OAR material and
retained raw/hash/seal evidence permitted by P5/P6.  P6's frozen statement is
binding: D6/parser/diagnoser/Agent/Advisor/screenshot are excluded as Observer
truth.  No P7 code may read them to determine `BLOCKED`, generate a label, or
become a truth-path input.

P6 synthetic/reference-only material and existing external P7 replay/source
material may be used only as format, parser, replay, provenance, and regression
inputs.  They cannot be upgraded to Observer truth, independent fault truth,
hardware validation, accuracy, recall, or a real-RTOS claim.  A synthetic,
replay, report-only, advisory, parser, diagnoser, Agent, Advisor, screenshot,
or model output must be explicitly labelled non-truth and remains permanently
ineligible for this upgrade.  Package/proof/closure status cannot override
`UNKNOWN`/`OOD` or create truth.

The older generic `docs/phase7_*` external-replay work is a distinct historical
Phase 7 stream.  It must not provide record IDs, source refs, claims, output
directories, schemas, or a substitute baseline for RTD-PILOT P7.

## 7. Implementation sequence and checks

1. Before writing, primary agent rechecks `HEAD`, frozen commit/tree,
   protected-path diff, P6 SHA-256 table, and `git status --short`; abort on
   any mismatch.  Existing user modifications are reported but never cleaned,
   staged, or read as P7 input.
2. Implement only the whitelist using P6 validator helpers/patterns.  The tool
   first validates P5/P6 and all source hashes, then independently establishes
   missing preconditions solely from frozen P6 scope/boundary fields, then
   exclusive-creates the P7 records in dependency order.  It has no hardware,
   serial, SWD, reset, flash, subprocess, network, model, Agent, Advisor,
   parser or diagnoser invocation.
3. Tests cover valid frozen intake -> `BLOCKED`, stale P6 hash rejection,
   noncanonical/superseded-run rejection, duplicate record ID rejection,
   no-overwrite, missing source-ref rejection, manifest completeness, parent
   chain, no absolute path, and forbidden-truth-source rejection.
4. Generate exactly one P7 run only after focused tests pass.  Recompute every
   generated hash and validate JSON/schema/manifest/identity/lineage/episode,
   duplicate/cross-case/stale-binding/split/no-overwrite properties.
5. Run the complete regression and protected-input recheck below.  On any
   failure, preserve records, write an append-only invalid/correction/blocked
   record only when factual and possible, and stop; do not fill gaps by
   inference.

## 9. Risks, blockers, stop/rollback, and dependencies

The immediate blocker is substantive, not a missing implementation detail:
there is no eligible independent real-hardware Case/Observer truth hierarchy or
Phase 6 target output admitted by P6.  It blocks baselines, ablations, fair
evaluation, split selection, scorer execution, and any P7 readiness claim.
Any P6/P5 hash/commit/tree mismatch, protected-file change, hardware request,
truth-path coupling, missing source, external dependency, attempted holdout
access, stale/cross-case binding, split error, or no-overwrite violation stops
the run.  Do not repair frozen inputs, tune a baseline, collect data, or make a
claim under those conditions.

Rollback means preserve all new append-only records and return to the frozen
commit as the logical baseline; it never means reset, clean, delete, amend, or
rewrite any user/P5/P6 material.  A later authorized correction is a fresh
record as described above.  The current P7 gate needs no new dependency,
hardware, external network, credentials, or human subject.  Completing the
governing P7 baseline/evaluation phase later requires explicit human approval
and independently valid Phase 5/6 prerequisites; it may also require
feasibility/license review for optional FO/MTL/TeSSLa, but those are expressly
outside this gate.
