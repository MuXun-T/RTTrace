# RTD-PILOT P7 Revised Plan: P5 Truth Admission and Evaluation Prerequisites

Status: planning only.  This document authorizes neither implementation nor a
formal P7 record.  It replaces the premise, not the retained history, of
`p7_plan_20260914T123520Z.md`.

## 1. Decision and scope

The prior P7 gate incorrectly concluded that P6 lacked a Phase 5 independent
Observer-truth hierarchy.  That conclusion conflicts with P6's canonical
binding to P5 and is not a valid blocker.  The P5 frozen record is
`record:p5-freeze-20260914T181500Z`; its collection gate states 12 positive
cases, 9 controls, 63 captures, three independent captures per case, and zero
blocking/major findings.  The bound P5 manifest contains valid Observer/OAR,
CVR, CaptureEpisode, lineage, and raw-hash chains for every capture.

P7 therefore has three deliberately separate deliverables:

1. append-only correction of the obsolete P7 `P5 truth absent` blocker;
2. read-only P5 evidence admission plus registry-case split audit; and
3. deterministic method-output production and evaluation only after the first
   two deliverables pass.

P5 Observer/OAR/CVR and retained raw/hash/seal evidence are admissible
**Observer truth**.  Deterministic method output is a new P7 derived artifact:
it may be compared to that truth, but is never itself Observer truth, does not
amend a P5 label, and does not establish diagnosis/root-cause correctness
outside the declared P7 comparison domain.

No hardware operation is authorized: no capture, flash, reset, serial, SWD,
or board access.  No D6, parser, diagnoser, Agent, Advisor, screenshot,
synthetic or model output may enter the Observer-truth path.

## 3. Completion criteria

P7 can freeze only when all criteria below are met.

1. P5/P6 commit, tree, frozen-directory hashes and protected-path diffs pass.
2. A P7 admission record passes schema, source hash, identity, lineage,
   episode, duplicate, cross-case, stale-binding, split, and no-overwrite
   audits, with zero unresolved eligible-capture gaps.
3. Split assignment is predeclared at the P5 **registry-case** level before
   method output is created; all capture attempts, retries and corrections for
   a registry case remain in exactly one split.  No raw bytes, truth labels or
   method outputs cross a split boundary.
4. Each method-output record is deterministic, versioned, source-bound to one
   admitted capture, explicitly `observer_truth: false`, and has a unique ID,
   input/output SHA-256, identity, lineage, capture episode and P5 parent.
5. Scoring consumes only the sealed split, admitted P5 truth and sealed P7
   output records.  It reports invalid/failed/retry/non-manifested outcomes;
   it does not infer missing outputs or labels.
6. Every new file is listed in its own unique run manifest; full regression,
   JSON validation and integrity audit pass; no protected input is modified.

Until criterion 4 is satisfied, P7 may complete its correction/admission audit
but remains `EVALUATION_BLOCKED`.  P6's scope is synthetic/report-only; its
absence of a frozen eligible deterministic method output is the remaining real
blocker, not absence of P5 truth.

## 5. Record contract and retention

Every P7 JSON record uses a specific `rtd-p7-*-v1` schema and includes:
`record_id`, `record_type`, `phase`, `created_at`, `append_only`, schema
version, `hardware_action: false`, repository-relative `source_refs` with
SHA-256 and role, `identity`, `lineage`, `episode`, and a parent P5/P6/P7
record ID.  Source paths must be reachable, relative, no-follow regular files;
absolute paths remain only inside immutable historical P5 material and are not
copied into P7 records.

Admission identity contains P5/P6 commit/tree, P5 freeze record ID, registry
case ID, capture ID and raw hash.  Its lineage references the matching P5
CaptureEpisode and lineage record.  Output identity additionally contains the
method/version/config digest and input hash.  Output lineage references its
admission and parent capture; `observer_truth: false` and
`truth_boundary: "derived method output; not Observer truth"` are mandatory.

The correction is a new `P7_CORRECTION` record referencing the obsolete P7
blocked record.  It leaves prior `BLOCKED`, `INVALID_NON_MANIFESTED`,
`SUPERSEDED_NON_MANIFESTED`, failed, retry, invalid, split-rejected and
non-manifested records retained.  A factual replacement uses `supersedes`; a
factual amendment uses `correction_of`.  No record is renamed, deleted or
rewritten.  Every run requires a newly generated nonexistent directory and
exclusive creation (`O_CREAT|O_EXCL` or equivalent).

## 6. Execution order and audit gates

1. Recheck P6 commit/tree and the table above; invoke the existing read-only
   P6 frozen-input audit.  Abort on any mismatch.
2. Create one correction record for the false P5-truth-absent premise and a
   manifest that includes it.  It must not over-correct the distinct missing
   method-output blocker.
3. Produce P7 admission inventory from only the canonical P5 manifest,
   identity audit, lineage inventory, final audit and freeze record.  Verify
   the 21 registry cases/63 captures, valid positive/control status, unique
   IDs/raw hashes, source reachability, parent/episode linkage and no gaps.
4. Create and seal a registry-case split declaration before processing any raw
   input.  Audit for duplicate membership, capture-level leakage, cross-case
   binding, stale hashes, F1/F2/F3/control balance feasibility and split
   completeness.  Infeasibility is a retained `P7_SPLIT_BLOCKED` record, not
   an invented split.
5. Only if admission and split pass, execute the approved deterministic method
   over the declared inputs.  Each attempt creates a separate output record;
   failure/retry stays in the same registry-case split and is retained.
6. Only sealed valid outputs enter scoring.  The evaluation audit recomputes
   source hashes, exact identities, lineage/episode parents, duplicate,
   cross-case, stale-binding, split, correction/supersession, no-overwrite and
   manifest completeness checks before a freeze recommendation.
