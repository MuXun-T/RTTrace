## 3. 设计文档目标与当时判断

### 3.1 设计文档要求的最终状态

按需求文档，当前 MVP `P0` 必达状态至少包括：

1. 采集、格式、解析、重建、指标、告警、可视化、回放、对比、导出、复现闭环。

4. 告警、诊断、导出、复现都能回链统一证据与上下文。
5. 满足第 `7` 章非功能门槛与第 `8` 章验收条件。

### 3.2 当时最准确的项目判断

在该时点，项目已经不再是“大面积主链路功能缺失”状态，而是：

**主链路功能基本具备，Linux formal `1GB` 已闭环，剩余阻塞主要集中在跨平台一致性、长稳、formal GUI FPS、Windows collector perf，以及少量控制面 freshness。**

换句话说：

1. 代码层面的 `MVP P0` 主路径已经具备工程可运行性。
2. 当时最主要的未闭环项不是“功能不存在”，而是“正式 external evidence 不完整”。
3. 不建议再以 Linux public rerun 作为后续主线。

### 3.3 本计划中的“交付”定义

为避免把“拿到一份 formal 结果”误写成“可以交付”，本计划统一采用以下口径：

1. “可交付”是指：可对外宣称当前仓库满足设计文档定义的 `MVP P0` 必达合同，并形成完整最终交付包。
2. 对所有必达 `FR / NFR`，最终都必须在权威追踪面中映射为 `closed`；仅有 artifact、仅完成执行、或仅得到 `failed / mismatch_detected` 结果，都不能直接视为可交付。
3. `failed` 的 formal verdict 只表示“问题已被正式测出并可审计定位”，后续必须进入整改与复测；除非需求/设计基线经过正式变更并同步修订，否则不得据此宣称“已达到设计文档要求”。

## 7. 总体执行策略

后续执行必须遵循以下策略：

1. 不再跑新的 Linux public rerun，除非 Windows formal 或 compare 暴露出新的代码级问题。
2. 所有 compare 必须建立在同一输入、同一批次、同一哈希前提下。
3. 不得把 synthetic/offscreen FPS 当 formal GUI FPS。
4. 不得把短时 soak 当 `24h` 长稳。
5. Windows 侧若先失败，优先排查环境、输入一致性和 artifact 批次，不要先怀疑主链路代码。
6. 所有 phase 的关闭条件都必须映射到“对应 requirement/NFR 已 closed”；`failed / mismatch_detected / reports_ready` 只代表阶段产物齐备，不代表可交付。
7. `docs/final_validation_status_20260314.json::external_pending` 必须覆盖全部未闭环项，不得低报。
8. 外部执行命令必须按权威文档逐字执行；Python 回归命令固定为 `python3 -m pytest tests/python -q`，不得随意替换为裸 `pytest`。
9. normalized package compare 必须基于显式保留的导出目录执行，不接受 `/path/to/...` 这类占位路径作为正式计划产物。

## 10. 风险与分支处理

### 10.1 Windows environment 风险

风险：

1. `PySide6 / pyqtgraph` 版本不一致
2. 输入文件复制错误
3. scratch 不是本地 SSD

处理：

1. 先跑 preflight / env
2. 再核对输入哈希
3. 最后再跑 runtime / perf / compare

### 10.2 compare 假失败风险

风险：

1. Linux / Windows 产物来自不同批次
2. `dataset_scale` 或 `sha256` 不一致

处理：

1. compare 前先核对 `acceptance_baseline.inputs.*sha256`
2. Linux 必须补同输入 acceptance baseline

### 10.3 长稳执行成本风险

风险：

1. `24h` 仍有执行成本
2. 途中失败难以归因

处理：

1. 采用阶梯时长
2. 每级都落 artifact
3. 优先保证 Windows `24h` long soak 与不可恢复错误观测完整留档；`collector_soak_windows` 作为 supporting evidence 同步保留

### 10.4 GUI FPS 口径风险

风险：

1. synthetic/offscreen 结果被误用为 formal GUI FPS

处理：

1. 在当时时点正式 GUI FPS 方案落定前，summary 保持 `linux_evidence_only`
2. 在当时时点不提前宣称 `NFR-PERF-05` 达标

### 10.5 命令与产物漂移风险

风险：

1. external 执行时把 `python3 -m pytest tests/python -q` 替换成其他入口，导致环境行为不同
2. compare 阶段继续使用占位路径，导致 package compare 无法真正落地

处理：

1. 在 phase0 固化精确命令，不允许执行入口漂移
2. package compare 必须使用本计划中明确生成的 `docs/package_windows_formal` 与 `docs/package_linux_formal`
