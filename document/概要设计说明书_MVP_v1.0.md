## 1. 引言

### 1.1 编写目的

本文档用于在软件设计 V 模型下完成本项目从需求规格到系统设计的承接，给出 MVP 阶段可直接指导详细设计、编码实现、集成测试与系统测试的总体设计方案。文档重点回答以下问题：

1. 系统由哪些子系统组成，各子系统承担什么职责。
2. 数据如何从目标端采集、编码、传输、解析、重建、分析、展示并导出。
3. 各模块之间通过什么数据契约和接口协同，如何保证跨模块口径一致。
4. 如何通过回放、对比、导出、复现形成可追溯、可举证、可复核的分析闭环。
5. 如何将概要设计成果与后续集成测试、系统测试、验收测试建立追踪关系。

### 1.2 适用范围

本文档仅覆盖 `MVP P0` 范围内的概要设计，包含以下能力：

1. UEOS 目标端运行时结构化日志采集与输出。
2. 日志统一格式规范、字典机制与兼容策略。
3. 离线解析与在线增量解析统一链路。
4. 跨核排序、时间对齐、状态重建与多维索引。
5. 指标统计、热点分析、轻规则诊断与证据反查。
6. 桌面分析端可视化联动、回放、双基线对比、导出与复现。

以下内容不在本文档设计范围内：

1. 第二个 RTOS 适配实现。
2. 集中式在线监控平台、多用户协同与远程统一管控。
3. 复杂规则引擎、自动根因推理与智能诊断编排。
4. 面向目标系统的运行时注入式日志重演与自动化实验脚本编排。

## 3. 需求概述与设计原则

### 3.1 建设目标

系统以“日志驱动监测内核”为核心思路，以操作系统运行过程中产生的结构化事件日志为唯一事实来源，完成“采集 → 格式 → 解析/对齐 → 状态重建 → 指标/诊断 → 展示 → 回放/对比/导出/复现”的完整闭环，实现对任务调度、同步竞争、中断行为与实时性问题的可观测、可度量与可追溯分析。

### 3.2 核心成功标准

1. 同一数据集在 Windows 与 Linux 上解析结果一致，在多次重复解析中排序与导出结果稳定一致。
2. 同一数据集在离线解析和在线增量解析两种输入形态下，排序、重建、指标、告警与导出口径一致。
3. 所有异常结论可通过证据链反查到时间窗、对象与关键事件区间。
4. 支持分析侧逐事件回放，且时间线、事件表、指标视图联动一致。
5. 支持 `baseline/candidate` 双运行基线同口径对比，并能对差异结果下钻举证。
6. 导出包和快照可重新打开，恢复分析上下文并复现告警、统计结果与导出结论。

### 3.3 总体设计原则

1. **离线优先，兼顾在线基础链路**：MVP 以离线文件分析为主，同时纳入文件、串口、网络三类输出与在线增量解析基础能力。
2. **统一数据基线**：解析、重建、指标、告警、回放、对比与导出共享同一 `UnifiedEventStream` 及其派生结果，禁止各子系统独立维护冲突口径。
3. **证据链闭环**：所有结论型输出必须可通过 `EvidenceRef` 回链到事件流、执行片段或索引对象。
4. **可信度显式化**：所有 CRC 损坏、序号缺口、溢出、截断、字典不匹配、对齐失败等问题必须形成 `UntrustedWindow` 并沿链路传播。
5. **目标端低侵入**：采集端关键路径不得动态分配、不得阻塞式 I/O、不得暴露半条记录。
6. **稳定排序优先**：无法完成跨核绝对对齐时，系统必须退化到 `timestamp → core_id → seq` 的稳定排序并显式声明降级状态。
7. **可复现与可审计**：导出包必须包含足以恢复上下文、校验结构、追踪来源的最小信息集合。

### 3.4 范围边界对设计的约束

1. 采集端语言固定为 `C/C++`，分析端固定为 `Python Qt`。
2. 回放限定为分析侧数据回放，不重注入目标系统，不重演调度执行。
3. 双运行基线对比是主能力，同库多窗口仅为辅助视图，不得替代对比结论。
4. `Trace` 导出要求可校验、可回链、与统一事件流同口径，但不绑定具体外部生态格式名称。

## 4. 系统总体设计

### 4.1 系统上下文

系统由目标端与分析端两大边界组成。

1. **目标端（UEOS/RTOS 内核侧）**：在调度点、上下文切换点、任务状态变化点、同步原语操作点、中断入口与出口等关键位置埋点，生成结构化事件，并通过文件、串口或网络输出。
2. **分析端（PC/上位机）**：接收离线日志或在线流，对日志进行解析、对齐、重建、统计、展示，并提供回放、对比、导出与复现能力。

### 4.2 系统总体架构

```text
+---------------------------+          +--------------------------------------+
|        目标端 UEOS        |          |             分析端 PC                |
|---------------------------|          |--------------------------------------|
| 采集埋点/钩子             |          | 解析与完整性处理                     |
| 每核无锁环形缓冲          |  日志    | 跨核排序与时间对齐                   |
| reserve-write-commit      | -------> | 状态重建与索引                       |
| 文件/串口/网络输出        |          | 指标统计与轻规则诊断                 |
+---------------------------+          | 多视图可视化                         |
                                       | 回放 / 对比 / 导出 / 复现            |
                                       +--------------------------------------+
```

### 4.3 部署架构

| 部署域 | 主要模块 | 运行特征 |
|---|---|---|
| 目标系统内核态 | 日志采集与生成 | 高实时约束、低侵入、无阻塞 |
| 目标系统用户态或导出器 | 输出通道管理 | 批量刷出、分段写入、滚动输出 |
| 分析工作站桌面端 | 解析、重建、统计、可视化、导出、复现 | 交互式分析、大数据量处理、多视图联动 |

### 4.4 分层架构

系统按职责划分为五层。

| 层级 | 内容 | 说明 |
|---|---|---|
| L1 数据采集层 | 埋点、缓冲、输出通道、过滤采样 | 位于目标端，负责产生原始结构化数据 |
| L2 数据契约层 | 全局头、事件头、Chunk 头、事件字典、兼容策略 | 贯穿目标端与分析端，确保同口径解析 |
| L3 数据处理层 | 解码、校验、排序、对齐、重建、索引 | 形成统一事件流与多维查询基线 |
| L4 分析诊断层 | 指标计算、热点分析、阈值告警、证据反查、差异计算 | 形成业务可用的统计与诊断结果 |
| L5 表现与交互层 | 时间线、曲线、事件表、资源图、回放、对比、导出、复现 | 面向最终用户提供交互式分析能力 |

### 4.5 端到端处理流程

```text
运行时事件发生
  -> 采集埋点触发
  -> 写入每核环形缓冲
  -> 批量刷出为 Chunk
  -> 文件/串口/网络输出
  -> 解析全局头与字典
  -> Chunk 校验与缺口识别
  -> 跨核排序与时间对齐
  -> 状态重建与索引构建
  -> 指标统计/诊断/告警
  -> 可视化联动
  -> 回放/对比/导出/复现
```

### 4.6 模块划分与职责矩阵

| 模块 | 核心职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| 日志采集与生成模块 | 捕获运行时关键行为，低侵入生成结构化日志 | 内核事件、配置、输出通道 | Chunk 化日志流、采集统计 |
| 日志事件模型与格式规范模块 | 定义统一契约、编码规则、兼容策略 | 事件语义、版本策略 | 标准事件记录、字典、校验规则 |
| 日志解析与状态重建模块 | 完成解码、校验、排序、对齐、重建、索引 | 日志文件或在线流、字典、配置 | `UnifiedEventStream`、`ExecSlice`、`TaskStateSeg`、索引、`UntrustedWindow` |
| 运行时指标统计与诊断模块 | 计算指标、识别热点、生成告警、输出证据链 | 统一事件流、重建结果、阈值配置 | 指标、告警、诊断结论、差异结果、`EvidenceRef` |
| 可视化分析与数据导出模块 | 展示与联动，提供回放、对比、导出与复现 | 数据基线、指标结果、上下文 | 交互界面、导出包、回放会话、复现输入 |

## 5. 各模块概要设计

### 5.1 日志采集与生成模块

#### 5.1.1 模块职责

1. 在调度、上下文切换、任务状态变迁、同步原语操作、中断进入退出等关键路径捕获事件。
2. 按统一事件格式将运行时行为写入每核无锁环形缓冲区。
3. 通过后台刷出机制输出文件、串口、网络三类日志通道。
4. 支持按事件、任务、核、对象进行过滤、采样与开关控制。
5. 统计丢包、溢出、写入量、输出量、时延等运行指标。

#### 5.1.2 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 内核埋点事件、采集配置、过滤策略、输出通道配置 |
| 输出 | Chunk 化结构化日志、丢包/溢出统计、采样命中标志 |

#### 5.1.3 内部子功能

1. **埋点触发器**：从内核关键路径提取最小必要上下文。
2. **事件组装器**：构造统一事件头与按类型载荷。
3. **环形缓冲管理器**：按核维护无锁缓冲区，采用 `reserve-write-commit` 写入协议。
4. **输出通道管理器**：批量刷出至文件、串口、网络，并支持分段和滚动输出。
5. **过滤与采样控制器**：在采集前或刷出前执行启停、过滤、采样策略。
6. **完整性统计器**：记录丢包、溢出、回绕、刷出延迟等运行情况。

#### 5.1.4 关键设计点

1. 关键路径只做快速写缓冲，不做阻塞式 I/O。
2. 关键路径禁止动态分配，缓冲区在初始化阶段一次性完成分配或绑定。
3. 刷出端只能看到已提交记录，不可见半条记录。
4. `auto_flush` 只能异步提出 flush 请求，不得把 drain/write 回流为当前 record 调用线程上的同步刷出。
5. 允许阻塞或等待的路径仅限于后台 flush worker 与控制面接口；fallback、retry/backoff 和 deadline 等慢路径不得进入 record path。
6. `trace_GetStats` 必须提供并发可读的聚合快照，用于观测 `lost / overflow / io_backpressure / written / flushed / latency` 等统计。
7. 高压场景允许降级为丢包和不可信标记，但不得破坏日志结构。
8. 所有缺口和溢出信息必须能够被分析端继承为 `UntrustedWindow`。

#### 5.1.5 对外接口

| 接口组 | 稳定接口能力 | 说明 |
|---|---|---|
| 控制类 | `trace_Init`、`trace_Enable`、`trace_Disable` | 负责采集模块初始化、全局或按核启停，以及停采后的缓冲保留/清理策略 |
| 记录类 | `trace_RecordEvent`、`trace_RecordTaskSwitch`、`trace_RecordTaskState`、`trace_RecordIRQ`、`trace_RecordSync` | 负责通用事件和关键调度/状态/中断/同步行为记录；专用记录接口可复用统一记录底座 |
| 过滤采样类 | `trace_SetFilter`、`trace_SetSampling` | 负责按事件/任务/核/对象维度过滤，以及比例/窗口/阈值采样策略的运行时生效 |
| 输出统计类 | `trace_FlushBuffer`、`trace_GetStats` | 负责批量刷出、输出通道协同与丢包/溢出/写入量/输出量/延迟等统计查询 |

概要设计阶段约束采集侧稳定接口边界与分组职责，不在本层展开各 `C API` 参数细节；参数、错误码和线程安全约束在详细设计中细化。

### 5.2 日志事件模型与格式规范模块

#### 5.2.1 模块职责

1. 定义全局头、事件头、Chunk 头及扩展载荷格式。
2. 定义 `EventID` 的 `Domain + Type` 编码规则。
3. 提供事件字典版本管理、编码解码和兼容策略。
4. 为解析侧提供跳读规则、校验规则和降级规则。

#### 5.2.2 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 事件语义定义、字段布局、版本演进策略 |
| 输出 | 格式规范、事件字典、编码记录、兼容策略 |

#### 5.2.3 内部子功能

1. **格式描述器**：定义头字段布局、字节序、时间单位和时钟源。
2. **字典管理器**：管理 `dict_ver`、事件类型、字段定义与扩展语义。
3. **编码器/解码器**：在目标端和分析端共享同一格式解释逻辑。
4. **Chunk 校验器**：按块执行 CRC 校验、序号范围检查与截断判断。
5. **兼容策略器**：处理未知事件、未知字段、字典缺失和版本不匹配场景。

#### 5.2.4 关键设计点

1. 事件头保留最小稳定字段，扩展字段通过载荷演进。
2. 未知事件或新版本字段必须可依赖 `payload_len` 跳读。
3. Chunk 是最小可校验、可截断恢复的单位。
4. 字典允许随文件携带或伴随文件提供，但必须与 `dict_ver` 一致可追踪。

#### 5.2.5 对外接口

| 接口 | 说明 |
|---|---|
| `spec_GetFormatVersion` | 返回文件/事件头版本号 |
| `spec_GetHeaderLayout` | 返回头字段布局、偏移和长度 |
| `spec_GetEventIdRule` | 返回 `EventID` 编码规则 |
| `spec_GetDictionary(dict_ver)` | 获取指定版本事件字典 |
| `spec_EncodeRecord(event_id, payload)` | 按规范编码记录 |
| `spec_DecodeRecord(bytes)` | 按规范解码记录 |
| `spec_VerifyChunk(chunk)` | 校验 Chunk 完整性并返回缺口信息 |
| `spec_CompatPolicy` | 返回兼容与降级策略 |

### 5.3 日志解析与状态重建模块

#### 5.3.1 模块职责

1. 支持离线多文件与在线流式两种输入形态的统一解析。
2. 完成全局头解析、字典绑定、Chunk 校验、序号连续性检查与缺口识别。
3. 基于同步锚点完成核间偏移校准，或在失败时退化为稳定排序。
4. 重建任务、核、资源和中断四类实体的时序状态。
5. 构建时间索引、对象索引与多级摘要，支撑交互式查询。

#### 5.3.2 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 日志文件、在线字节流、事件字典、解析配置 |
| 输出 | `UnifiedEventStream`、`ExecSlice`、`TaskStateSeg`、`ResourceGraph`、`IrqSpan`、索引、`UntrustedWindow` |

#### 5.3.3 内部子功能

1. **输入适配器**：统一文件、串口、网络三类输入形态。
2. **解码与校验器**：解析全局头、事件头、Chunk，并识别损坏和截断。
3. **对齐与合并器**：按 `timestamp → core_id → seq` 规则稳定合并，多核对齐优先使用同步锚点。
4. **状态机重建器**：维护任务状态、执行片段、资源持有等待关系与中断嵌套关系。
5. **索引构建器**：构建时间、任务、核、事件类型、资源、中断等索引与摘要。
6. **查询服务**：面向上层提供按时间窗、任务、核、对象和类型的统一查询。

#### 5.3.4 关键设计点

1. 离线解析与在线增量解析必须输出同口径结果。
2. 缺口区间不得输出错误状态推断或误导性派生结果。
3. 校准失败时不得伪造全局绝对时间真值，只能退化并显式标记。
4. `UnifiedEventStream` 是后续所有处理的唯一时间基线。
5. 索引必须支持大日志下的分页、局部加载和视图快速跳转。

#### 5.3.5 对外接口

| 接口 | 说明 |
|---|---|
| `prs_Init(cfg, dict)` | 初始化解析器与字典 |
| `prs_FeedChunk(core_id, bytes)` | 输入离线或在线统一 Chunk |
| `prs_Finalize()` | 完成输入并输出缺口与损坏统计 |
| `aln_Calibrate(sync_events)` | 基于同步锚点计算核间偏移与漂移 |
| `aln_Merge(per_core_events)` | 生成 `UnifiedEventStream` |
| `rb_Rebuild(unified_events)` | 生成执行片段、状态段、资源关系与中断区间 |
| `idx_Build(results)` | 生成正式 `IndexBundle` 索引结果与摘要 |
| `qry_Query(filter, range)` | 查询指定时间窗与条件下的事件/片段/对象结果 |

### 5.4 运行时指标统计与诊断模块

#### 5.4.1 模块职责

1. 基于统一事件流与重建结果计算任务级、核级、对象级指标。
2. 输出趋势、分布、`TopN` 热点与差异摘要。
3. 通过阈值和轻规则生成告警与诊断结果。
4. 将诊断结果与 `EvidenceRef` 绑定，支持异常反查与下钻举证。
5. 支持双运行基线的同口径差异对比。

#### 5.4.2 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | `RebuildBundle`（内含统一事件流、重建对象、数据集身份以及必要的 header / segment lineage 信息）、规则阈值 |
| 输出 | 指标曲线、分布统计、热点列表、带严重度与 `support_level` taxonomy 的告警和诊断结论、差异结果 |

#### 5.4.3 内部子功能

1. **任务指标计算器**：计算响应时间、抖动、就绪等待、阻塞、截止期违约等。
2. **核指标计算器**：计算利用率、空闲率、上下文切换、抢占密度、核间不均衡等。
3. **对象指标计算器**：计算竞争次数、等待时间、持有时长、队列长度峰值、热点对象 `TopN`。
4. **中断指标计算器**：计算中断占用比例、嵌套深度峰值、持续时间和对任务延迟的扰动关联。
5. **告警评估器**：执行阈值规则，输出严重度、`Alert.support_level`、对象、时间窗与建议反查路径。
6. **诊断归因器**：对异常窗口进行反查，生成证据链、可解释结论和与告警一致的 `support_level` 对外语义。
7. **差异计算器**：在 `baseline/candidate` 上执行同口径对比。

#### 5.4.4 关键设计点

1. 所有统计必须以统一时间基线和统一上下文为前提。
2. `UntrustedWindow` 必须进入指标与告警阶段，抑制误告警与错误归因。
3. 告警和诊断必须同时提供结论与证据，不允许只有结论没有来源。
4. 对比结果必须与双方单独统计结果保持同口径一致。
5. `CompareScope.dimensions` 必须真实驱动正式差异产物：`metric / alert / hotspot / interval / task / core / resource / irq` 分别映射到对应 `*_changes` 与 detail 维度，不得只保留输入枚举。
6. 统计模块开发、联调和验收统一以 `metric_Ingest(rebuild_bundle)` 为标准入口，禁止回退到私有三参数接口。

#### 5.4.5 对外接口

| 接口 | 说明 |
|---|---|
| `metric_Init(cfg)` | 初始化指标、阈值与规则配置 |
| `metric_Ingest(rebuild_bundle)` | 接入完整 `RebuildBundle`，作为统计层统一开发与联调入口 |
| `metric_Compute(t_begin, t_end, filter)` | 生成指标序列、分布与 `TopN` |
| `metric_Compare(baseline, candidate, scope)` | 生成双基线差异指标、热点与关键区间结果 |
| `alert_Evaluate(t_begin, t_end, filter)` | 执行阈值与轻规则检测并输出带严重度与 `Alert.support_level` 的告警 |
| `diag_Generate(t_begin, t_end, alert_list)` | 生成诊断结论并挂接证据链 |
| `diag_Backtrace(diag_id / alert_id)` | 返回异常反查所需证据引用 |
| `metric_Export(format, scope, t_begin, t_end)` | 导出指标、热点与告警结果 |

### 5.5 可视化分析与数据导出模块

#### 5.5.1 模块职责

1. 提供多视图联动的桌面分析界面。
2. 基于统一上下文驱动时间线、指标曲线、事件表、资源关系和告警面板协同工作。
3. 提供书签与证据链锚点导航能力。
4. 提供逐事件回放能力。
5. 提供双运行基线对比能力。
6. 提供全量导出、裁剪导出和复现包重开能力。

#### 5.5.2 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 数据基线、指标/告警结果、`AnalysisContext`、书签、用户交互 |
| 输出 | 图形界面视图、回放会话、差异视图、导出包、复现结果 |

#### 5.5.3 内部子功能

1. **工作区管理器**：维护工作区、布局和上下文。
2. **时间线引擎**：按核或按任务展示 `ExecSlice`、阻塞区间与中断区间，并支持 `LOD`。
3. **指标视图引擎**：展示趋势曲线、峰值和统计分布。
4. **任务状态视图引擎**：使用专用 `TaskStateQuery` 查询对象提供独立任务状态视图。
5. **事件表与检索引擎**：按时间、任务、核、类型、对象分页查询。
6. **资源关系视图**：展示等待链、持有关系与热点对象下钻。
7. **告警面板**：展示告警摘要、严重度、支持度和证据锚点。
8. **书签/锚点管理器**：保存轻量导航上下文，支撑从书签、告警、事件行与峰值入口回跳证据链。
9. **回放控制器**：管理播放、暂停、逐事件前进、逐事件后退和锚点定位，并只对外暴露最小 `PlaybackState`。
10. **对比工作区**：载入 `baseline/candidate`，展示差异摘要和明细。
11. **导出与复现控制器**：写出导出包，重开复现包并恢复上下文。

#### 5.5.4 关键设计点

1. 所有视图共享同一 `AnalysisContext`，任意入口跳转都必须驱动全局联动。
2. 曲线峰值、告警条目、事件行、书签四类入口必须共用同一证据链跳转机制。
3. 书签仅保存轻量导航上下文与证据锚点，不替代导出快照或复现包。
4. 回放过程中的时间线、事件表、指标视图必须同步更新。
5. 导出包必须是不可变快照，导出过程中用户操作不得影响当前包内容。
6. 裁剪导出必须保留与导出窗口相交的不可信窗口和必要上下文。
7. 复现包重开后必须恢复 `time_window`、`filter`、`selection`、`zoom_level` 与证据落点。
8. `viz_LoadDatasetAsync` 必须先交付 `LoadPreview / ReadinessState`，明确 `preview_ready` 与 `query_ready` 的边界；首屏 preview 不得伪装成全量查询已就绪。

10. `viz_QueryTaskStates` 必须使用专用 `TaskStateQuery`，不得复用时间线私有查询参数。
11. 回放接口统一返回最小 `PlaybackState`，不暴露内部运行态细节。

## 6. 核心数据与数据流设计

### 6.1 核心数据对象关系

```text
日志文件/在线流
  -> GlobalHeader + Chunk + EventRecord
  -> UnifiedEventStream
  -> ExecSlice / TaskStateSeg / ResourceGraph / IrqSpan
  -> MetricResult / Alert / Diagnosis
  -> Bookmark + AnalysisContext + EvidenceRef + UntrustedWindow
  -> Visualization / Replay / Compare / Export / Reproduce
```

### 6.2 全局头设计

全局头字段如下。

`magic endian time_unit clock_source format_ver dict_ver producer_ver run_id?`

设计要求：

1. 全局头必须位于日志文件头或流元信息起始位置。
2. 解析器据此识别字节序、时间单位、时钟源和格式版本。
3. `run_id?` 为可选运行追踪字段；存在时必须能在解析、导出与复现链路中保持可追踪性。
4. 事件字典可内嵌或伴随提供，但必须与 `dict_ver` 对齐。

### 6.3 事件头与 Chunk 设计

#### 6.3.1 事件头最小字段

`ver flags core_id event_id seq timestamp payload_len`

设计要求：

1. `event_id` 采用 `Domain + Type` 编码。
2. `timestamp` 必须单调递增，并显式声明单位与时钟源。
3. 解析端必须基于 `payload_len` 具备跳读能力。
4. 可选字段可包含 `magic` 或 `header_crc`，但不替代块级 CRC。

#### 6.3.2 Chunk 头字段

`chunk_start_ts chunk_end_ts core_mask/core_id record_count chunk_crc`

设计要求：

1. 推荐补充 `seq_range`、`dict_ver` 等辅助字段。
2. Chunk 是最小可校验、可恢复、可裁剪单元。
3. CRC 失败、截断和序号跳变必须产生缺口或损坏标记。

### 6.4 统一分析数据基线

| 数据对象 | 说明 | 主要来源 | 主要用途 |
|---|---|---|---|
| `UnifiedEventStream` | 全局稳定排序后的统一事件流 | 解析与合并 | 所有后续分析唯一时间基线 |
| `ExecSlice` | 任务在核上的运行片段 | 调度重建 | 甘特图、利用率、回放 |
| `TaskStateSeg` | 任务状态区间 | 任务状态机重建 | 阻塞、等待、响应分析 |
| `ResourceGraph` | 资源持有和等待关系 | 同步原语事件重建 | 锁竞争与等待链分析 |
| `IrqSpan` | 中断进入退出与嵌套区间 | 中断事件重建 | 中断占用与干扰分析 |
| `RebuildBundle` | 带数据集身份和可选 header / 索引附件 lineage 的完整结果包 | 解析与重建 | 统计、导出、复现与联调统一输入 |
| `IndexBundle` | 查询加速的派生索引结果 | 索引构建 | 可视化、跳转、分页查询 |
| `LoadPreview / ReadinessState` | staged-load 的正式首屏合同 | prescan / async load | 区分 `preview_ready`、`parse_rebuild` 与 `query_ready` |
| `TaskStatePreview` | 首屏任务状态摘要 | `LoadPreview` preview | 在 `preview_ready` 阶段提供任务状态最小可见结果 |
| `Bookmark` | 轻量导航书签与证据锚点引用 | 工作区交互、告警/事件入口 | 书签回跳、证据链定位、复核导航 |

### 6.4.1 MVP P0 事件字段冻结摘要

为保证 `collector / codec / parser` 并行推进，`TASK_READY`、`TASK_BLOCK`、`TASK_WAKEUP`、`CTX_SWITCH`、`IRQ_ENTER`、`IRQ_EXIT`、`LOSS`、`OVERFLOW` 的字段名、必填/可选、类型、语义和兼容策略在详细设计附表冻结。概要阶段固定以下约束：

1. 编解码顺序以冻结字段顺序为准，新增字段只能后向追加为可选字段。
2. 必填字段缺失必须显式报错并产生不可信标记，禁止静默填充业务默认值。
3. 枚举字段只允许新增取值，不得重释既有取值语义。

### 6.5 证据引用与不可信窗口设计

#### 6.5.1 `EvidenceRef`

`EvidenceRef = { ref_type, ref_key, t_begin, t_end }`

设计要求：

1. `ref_type` 至少支持 `event`、`slice`、`index`。
2. 告警、诊断、书签、回放锚点和导出元信息必须可关联 `EvidenceRef`。
3. `ref_key` 必须能回溯到统一事件流、执行片段或索引对象。

#### 6.5.2 `UntrustedWindow`

`UntrustedWindow = { window_id, source, scope, t_begin, t_end, reason_code, severity }`

设计要求：

1. `source` 至少支持 `crc_fail`、`seq_gap`、`overflow`、`truncate`、`dict_mismatch`、`align_fail`、`open_relation`。
2. `scope` 至少支持 `event`、`rebuild`、`metric`、`alert`、`viz`、`export`。
3. 解析、重建、统计、可视化、导出必须共享同一 `UntrustedWindow` 口径。
4. 裁剪导出必须保留与导出窗口相交的 `UntrustedWindow` 信息。

### 6.6 书签与分析上下文设计

#### 6.6.1 `Bookmark`

`Bookmark = { bookmark_id, label, time_window, filter, selection, focused_view, evidence_anchor }`

设计要求：

1. 书签至少保存 `time_window`、`filter`、`selection` 与 `evidence_anchor`，用于轻量导航回跳。
2. 曲线峰值、告警条目、事件行、书签四类入口必须可统一解析为书签/锚点导航动作。
3. 书签用于复核导航，不作为不可变快照或复现包的替代物。
4. 书签恢复后的上下文必须与当前工作区 `AnalysisContext` 合并生效，并保留证据链落点。

#### 6.6.2 `AnalysisContext`

`AnalysisContext = { time_window, filter, selection, zoom_level, focused_view, evidence_anchor, playback_cursor, compare_scope }`

设计要求：

1. 回放、导出、复现与可视化联动必须共享同一上下文模型。
2. `compare_scope` 至少记录 `baseline_id`、`candidate_id`、比较维度和对齐时间窗。
3. 书签可保存轻量导航上下文，但不可替代快照或复现包。
4. 复现包重新载入后必须恢复到可复核、可举证的分析状态。

### 6.7 导出包结构设计

导出包采用多文件目录结构。

1. `meta.json`
2. `event/`
3. `rebuild/`
4. `result/`
5. `context/`
6. `manifest.json`

其中：

| 路径 | 内容 |
|---|---|
| `meta.json` | 时间/解析基线、导出范围与快照、运行/版本/参数追踪、分析上下文与证据锚点、比较角色、导出来源；裁剪导出额外包含补边规则与不可信窗口 |
| `event/` | 统一事件流导出，采用 `JSONL` 或 `Trace` |
| `rebuild/` | 执行片段、任务状态、资源关系、中断区间等重建结果 |
| `result/` | 指标表、分布结果、热点列表、告警与诊断结果 |
| `context/` | `analysis_context.json`、`anchors.json` 等复现上下文 |
| `manifest.json` | 文件清单、条数、校验和、版本信息 |

设计要求：

1. `Trace` 导出必须来源于统一 `UnifiedEventStream`。
2. 导出内容必须能与 `manifest.json` 及 `EvidenceRef.ref_key` 建立回链关系。
3. 导出包必须支持脱离界面独立校验、二次分析与重新载入。
4. 复现包必须保留恢复分析上下文与证据锚点所需的最小信息集合。
5. 快照必须是不可变内容集合，保证导出一致性与复现一致性。

`meta.json` 在概要设计阶段至少约束以下必选元数据类别：

1. **时间与解析基线类**：`time_unit`、`clock_source`、`align_policy`、`dict_ver`、`parser_ver`，用于声明时间口径、字典口径和对齐降级策略。
2. **导出范围与快照类**：`export_scope`、`export_time`、`time_window`、`filter`、`selection`、`zoom_level`、`snapshot_id`，用于标识一次不可变导出快照及其界面范围。
3. **运行追踪类**：`run_id`、`run_batch_id`、`version_id`、`experiment_params`，用于支撑运行批次、版本基线与参数可追踪性。
4. **分析复核类**：`analysis_context`、`evidence_anchor`、`export_source`，用于复现包重开、上下文恢复与导出来源追踪。
5. **对比角色类**：`compare_role`，取值至少支持 `baseline`、`candidate`、`single`，用于双基线导出的角色还原。
6. **裁剪导出补充类**：`context_padding_rule`、`untrusted_windows`，用于记录窗口补边规则以及与 `UntrustedWindow` 同口径的不可信区间。

## 7. 接口概要设计

### 7.1 外部接口设计

| 外部接口 | 交互对象 | 设计说明 |
|---|---|---|
| 内核埋点接口 | UEOS 调度器、同步原语、中断处理逻辑 | 提供最小侵入式采集点，不改变原始调度语义 |
| 日志输出接口 | 文件、串口、网络 | 支持离线留存与在线流式接入 |
| 日志输入接口 | 日志文件、在线数据流、导出包 | 统一为 Chunk/包级输入，不暴露实现差异 |
| 桌面交互接口 | 用户操作、工作区、查询控件 | 所有视图共享统一上下文 |
| 导出复现接口 | 本地文件系统、外部分析工具 | 通过标准数据包实现独立校验与重开复现 |

### 7.2 内部接口分组设计

#### 7.2.1 采集侧接口组

采集侧接口负责目标端运行时日志产生，是数据链路起点。

接口边界按稳定能力分为四组：

1. **控制类接口**：负责 `trace_Init`、`trace_Enable`、`trace_Disable` 等初始化与启停控制。
2. **记录类接口**：负责 `trace_RecordEvent` 及任务切换、任务状态、中断、同步等专用记录入口。
3. **过滤采样类接口**：负责 `trace_SetFilter`、`trace_SetSampling` 等运行时策略控制。
4. **输出统计类接口**：负责 `trace_FlushBuffer`、`trace_GetStats` 等刷出和运行指标查询。

#### 7.2.2 格式规范接口组

格式规范接口负责维护采集端与分析端共享的数据契约，是跨模块一致性的基础。

#### 7.2.3 解析重建接口组

解析重建接口负责从原始日志到统一分析基线的转换，是后续统计与展示的桥梁。

#### 7.2.4 统计诊断接口组

统计诊断接口负责将状态重建结果转化为指标、告警和诊断结论。

#### 7.2.5 可视化与复现接口组

可视化与复现接口负责面向用户的交互、书签导航、回放、对比、导出和上下文恢复。

### 7.3 接口设计原则

1. 接口命名统一按功能域分组，如 `trace_*`、`spec_*`、`prs_*`、`metric_*`、`viz_*`。
2. 上层模块只能消费下层稳定产物，不得绕过数据基线直连原始输入。
3. 导出、复现、回放、对比不得创建与主分析链路不一致的私有数据模型。
4. 接口返回结果必须携带必要的可信度标记或错误信息，避免静默失败。

## 8. 非功能与异常处理设计

### 8.1 性能设计

| 非功能目标 | 设计支撑 |
|---|---|
| 采集吞吐 `>= 1,000,000 events/s` | 每核无锁环形缓冲、批量刷出、关键路径最小字段写入 |
| 采集路径不阻塞 | 禁止关键路径动态分配和阻塞式 I/O |
| `1GB` 日志首屏 `< 10s` | 多级索引、首屏摘要、异步补齐、分页加载 |
| 内存占用 `< 4GB` | LOD 数据裁剪、索引分层、按需载入 |
| 时间线 `>= 30 FPS` | LOD 聚合、图块化渲染、视图增量更新 |
| `1GB` 全量导出 `<= 60s` | 批量序列化、快照冻结、分层导出 |
| `10` 分钟窗口裁剪导出 `<= 15s` | 基于时间窗索引的裁剪读取、上下文补边复用、只导出相交 `UntrustedWindow` 与必要依赖 |

### 8.2 一致性设计

1. 同一输入在 Windows 与 Linux 上共享同一解析、排序、重建与导出规则。
2. 稳定排序规则固定为 `timestamp → core_id → seq`。
3. 离线与在线两条链路共用统一输入抽象、统一重建与统一指标计算器。
4. 复现包重开后必须恢复相同的 `AnalysisContext` 和相同的分析基线。
5. 双基线对比结果必须与各自单独统计结果同口径。
6. 统计层入口统一为 `metric_Ingest(rebuild_bundle)`；需求、概要、详细设计与自测按同一口径描述。

### 8.3 兼容性设计

1. 未知事件和未知字段必须可跳读降级。
2. 字典缺失时至少保留基础头字段解析能力，并产生显式告警。
3. 版本演进以“新增可跳过、旧版可退化”为基本兼容策略。

### 8.4 异常处理与降级设计

| 异常场景 | 处理原则 | 结果表现 |
|---|---|---|
| Chunk CRC 失败 | 标记损坏区间，禁止错误推断 | 产生 `UntrustedWindow`，界面提示 |
| `seq` 跳变 | 识别缺口，抑制跨缺口状态推断 | 产生 `UntrustedWindow`，影响相关结果可信度 |
| 缓冲溢出 | 保留溢出计数与来源 | 导致相关时间窗不可信 |
| 日志截断 | 尽可能恢复可解析部分 | 对截断尾部打标并终止完整性推断 |
| 字典缺失/版本不匹配 | 基础字段降级解析 | 语义分析降级并提示 |
| 对齐失败或无锚点 | 不宣称绝对时间真值 | 退化为稳定排序并标记对齐降级 |
| 开放等待链/异常 IRQ 栈 | 不输出武断结论 | 标记 `open_relation`，提示人工复核 |

### 8.5 稳定性设计

1. 系统按 `24h` 长稳目标设计，前后台线程、导出任务和回放任务都必须具备可监测、可终止、可恢复的生命周期管理。
2. 长稳运行期间出现日志损坏、解析失败、导出失败或对齐失败时，必须限制影响范围到当前任务或时间窗，不得演变为不可恢复错误。
3. 采集端与分析端都必须保留关键运行统计、错误计数和最近一次失败原因，支撑长稳问题复盘与恢复。
4. 后台任务异常退出后必须通过显式错误状态反馈到界面或调用方，禁止静默失效。

### 8.6 可维护性设计

1. 模块按职责边界清晰分层，减少跨层耦合。
2. 所有核心结果对象均通过统一契约表达，便于扩展更多 RTOS 与更多视图。
3. 接口命名和数据结构保持稳定，便于版本迭代与测试复用。

5. 必须验证异常场景下的显式降级与不可信标注，不允许伪造结果真值。

## 11. 结论

本概要设计以统一数据基线、统一上下文、统一可信度机制和统一证据链为核心，将目标端采集与分析端闭环能力纳入同一系统架构中，满足 MVP 阶段“可采集、可解析、可重建、可诊断、可展示、可回放、可对比、可导出、可复现”的总体目标。后续详细设计应在不突破本文档架构边界和契约约束的前提下，进一步细化模块内部类、数据结构、线程模型、序列化细节和测试实现。
